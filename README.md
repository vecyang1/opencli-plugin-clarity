# opencli-plugin-clarity

An [OpenCLI](https://github.com/jackwener/OpenCLI) adapter that reads Microsoft
Clarity's **project settings** — the integration status for Google Analytics,
Google Tag Manager, Google Ads and Microsoft Ads — across every project on an
account.

Clarity has no API for this. Not the Data Export API, not the official MCP
server, not any third-party wrapper. Settings are dashboard-only, so these
commands read the rendered page through a Chrome session you are already signed
in to. **Read-only: nothing here connects, disconnects or changes anything.**

## Install

```bash
opencli plugin install github:vecyang1/opencli-plugin-clarity
```

Or copy the `.js` files into `~/.opencli/clis/clarity/` by hand — that is the
same directory layout and needs no plugin machinery.

Requires OpenCLI with its Chrome extension bridge working (`opencli doctor`
green) and Chrome signed in to Clarity.

```bash
opencli clarity integrations a1b2c3d4e5          # one project
opencli clarity projects -f json                 # every project + its id
opencli clarity audit --only-issues -f table     # all projects, flag what needs setup
opencli clarity audit --project-ids a1b2c3,d4e5f6
opencli clarity traffic --range "Last 30 days"   # sessions/users per project
```

`audit` answers "is this project *configured*". `traffic` answers "does anyone
actually use it". They disagree usefully: a project can be fully wired to GA and
GTM and have had zero visitors all month, which makes its "setup needed" sibling
not worth fixing first.

## Why this exists — what the official surfaces do *not* cover

Measured 2026-08-24.

| Surface | Covers | Covers integrations? |
|---|---|---|
| Clarity **Data Export API** (`Settings → Data Export` token) | aggregate metrics, ≤3 days, ≤3 dimensions, **10 req/project/day** | **No** |
| Undocumented **`clarity.microsoft.com/mcp/*`** (what the official MCP server actually calls) | session-level metrics, **365-day** window, separate quota pool | **No** |
| Official **`@microsoft/clarity-mcp-server`** | a client for the `/mcp` surface above | **No** |
| `clarity-api` (PyPI), Composio toolkit | the Data Export API again, 10/day cap inherited | **No** |

**Correction, 2026-08-25.** An earlier version of this file claimed the official
MCP server "wraps the same Data Export API". That was inferred from Microsoft's
docs and third-party descriptions, and it is wrong. This was measured directly — the package contains no `clarity.ms` string and calls
`clarity.microsoft.com/mcp/*`, which is a **different surface** with a separate
quota and a 365-day window. **For reading behaviour on a single project, use the `/mcp` surface
directly (or the official MCP server), not this adapter.**

What survives that correction is the reason these commands exist: **no surface,
documented or not, exposes project settings.** The `/mcp` surface advertises
three tools — dashboard query, recording list, docs search — none of which
touches tag installation or project configuration.
Integrations, masking, IP blocking and team are UI-only, which is why `audit`
and `integrations` drive the rendered page.

### Where `traffic` still earns its place — and where it does not

The `/mcp` surface is the better instrument for one project: deeper data, no
browser, no bridge. Use it for anything qualitative.

The one thing it cannot do cheaply is a **whole-account sweep**. The `/mcp`
token carries its project in the `sub` claim and takes no project parameter, so
20 projects means 20 tokens generated by hand in the dashboard and 20 server
registrations. `clarity traffic` answers "which of my 20 projects has anyone on
it" in one pass with zero provisioning. That is its whole niche; past it, reach
for `/mcp`.

## The internal GraphQL endpoint, and why it is not used

Clarity's dashboard talks to `POST https://clarity.microsoft.com/api/v2`
(Apollo). The operation for this exact page exists and was recovered from the
client bundle:

```graphql
query getProjectIntegrationsData($projectId: String!) {
  project(id: $projectId) { id, integrationsInfo { integrations { id enabled integrationType extraInfo { myShopifyDomain siteUrl } } } }
}
```

368 operations were recovered the same way (`getGTMInfo`, `getIntegrationInfo`,
`linkGoogleAnalytics`, …). **They are not callable from outside the app.** Every
hand-built request returns a flat `400 Bad Request` — including a bare
`{ __typename }`, which is why this is a transport-level rejection and not
query validation. Ruled out by varying one input at a time, all still 400:

- batched array body, `operationName` + `variables`, `x-requested-with`, `accept: application/json`
- `X-CSRF-Token` read from the page's own `meta[name=csrf-token]`
- `x-clarity-version: 2` (the header name resolved out of the bundle)

Because the endpoint rejects before parsing, **schema-recovery tooling that
relies on GraphQL "did you mean" suggestions — e.g. `clairvoyance` — cannot
work here.** The bundle already gave the exact operations for free; the missing
piece is the request signature, not the schema. If that signature is ever
recovered, swapping these commands to GraphQL would remove the page loads.

## Reading notes

- **`Unknown` is not `Not Connected`.** A card the page did not render is
  reported `Unknown` and never counted as "needs setup" — otherwise a layout
  change would send you to reconnect something that was already fine. For the
  same reason `readIntegrationCards` **throws** on zero cards instead of
  returning `[]`: an empty list renders as "this project has no integrations",
  which is a different and wrong claim.
- Status is parsed from the panel's **line order** (the pill is the line above
  `<Name> integration`), not the DOM tree. Walking up from the title lands on a
  container holding several cards, which loses the status for exactly the
  connected ones.
- **The wait marker must be a specific card title.** Waiting on a loose
  `' integration'` matched a panel that had painted only some of its cards, and
  the parser then returned a *confident wrong* status — a full audit reported
  `one project` as "GA Not connected" when GA and GTM were both Connected.
  That is far worse than an unreadable page, because it sends you to reconnect
  something that already works. The marker is now
  `Google Tag Manager integration`, and `readIntegrationCards` **refuses** any
  read that does not contain all four expected cards. Partial renders do not
  degrade to `unknown` on their own — they have to be made to.
- **The end marker is not the end of the render.** The Setup panel's cards paint
  progressively and `Advanced settings` can appear *before* the last card lands,
  so "end marker present + at least one card" still accepted a half-painted
  panel — and every card that had not arrived yet was reported `Not offered`,
  i.e. a present integration recorded as absent. Two projects (two of them)
  were filed as "needs Google Analytics" when GA was already connected.
  `readIntegrationCards` now requires the **card count to hold steady across two
  polls** before it trusts a read. The general shape: an end-of-content marker
  proves the container finished, never that its children did.
- **"Not signed in" is only credible if nothing else read.** One project
  returned Clarity's signed-out shell while 19 others in the same run read fine
  — the session was healthy and the account simply cannot open that project.
  `audit` now relabels those rows `no access` at the end of the run, because
  "sign in again" is the wrong remedy and the user will do it twice before
  doubting the message.
- **`traffic` reads back the applied date range and refuses a mismatch.** The
  `?date=` parameter is honoured today, but a silently clamped or ignored window
  would label last-3-days numbers as "Last 30 days", and nobody re-runs a green
  check. The page prints the window next to `Segments`; that is the receipt.
- **A short project list is a wrong answer, not a small one.** Two consecutive
  discovery runs returned 20 ids and then 3, and the audit reported the 3 as if
  they were the whole account. `discoverProjects` now settles — it re-harvests
  until the id count is unchanged twice running *and* is at least the number of
  site lines rendered — and the caller rejects any sample with fewer ids than
  rendered cards. When discovery still cannot settle, pass `--project-ids`.
- `?cb<projectId>=1` in the settings URL is deliberate. Clarity is hash-routed,
  so navigating between two projects' `#setup` pages without a differing query
  string does not reload — you would silently re-read the previous project.
- **`siteSession` must be `ephemeral`.** Under `persistent` the adapter got a
  context that was *signed out* while the same Chrome profile was signed in
  everywhere else. The symptom is deliberately confusing and worth recognising:
  `location.href` is the app URL you asked for, `document.body.textContent` is
  ~3.8 kB, and `document.body.innerText` is **empty** — because the marketing
  homepage rendered without layout. `document.title` is the only field that
  tells the truth (`Microsoft Clarity - Free Heatmaps & Session Recordings`),
  so the signed-out check reads the title, not the body.
- **Wait inside the page.** Every wait is an `async` IIFE in `page.evaluate`
  polling for a marker. (`page.wait` does exist on this page object — an early
  guess that it did not was wrong, and cost a debugging round. The real cause of
  the blank reads was the signed-out context above.)
- **Deterministic project discovery.** Each card on the Clarity grid renders
  `data-clarity-id="projectClicked_<projectId>"`, pairing project ID, friendly name,
  and site URL deterministically without fragile fiber inspection. If redirected to a
  specific project dashboard, `discoverProjects` clicks "My Projects" to return to
  the grid.
- **Fast `NOT_FOUND` exit.** When navigating to a non-existent or unauthorized project
  ID, Clarity renders `"This project doesn't exist or you don't have permissions to view it."`
  without changing `location.href`. The adapter detects this within 1–2s and breaks
  immediately, avoiding wasted second retry attempts.
- **Navigation resilience (`safeGoto`).** Direct navigation often triggers SPA redirects
  or container reuse that can throw `Navigation rejected`, `Detached while handling command`,
  or `Debugger is not attached`. `safeGoto` recovers transparently via in-page evaluation,
  settling delay, and new-tab fallback.
- Clarity is usually installed **through GTM**, not as a static snippet, so you
  cannot recover a project id by fetching the site's HTML — none of 20 sites
  carried `clarity.ms/tag/<id>`.

## Runtime, and why a whole run can be lost

A healthy project reads in ~10 s. A project whose Setup panel never paints
costs the full in-page wait (20 s) twice, because of the retry — so the run
time is set by how many projects fail, not by how many there are.

`audit` returns only when every project is done, so **a command-level timeout
discards the whole run.** A 20-project sweep with a 45 s wait hit
`OPENCLI_BROWSER_COMMAND_TIMEOUT=2400` and produced nothing at all. Give it
headroom, and for a large account prefer batches you can keep:

```bash
opencli clarity audit --project-ids "$(sed -n 1,10p ids.txt)" -f json > batch1.json
opencli clarity audit --project-ids "$(sed -n 11,20p ids.txt)" -f json > batch2.json
```

## Running it

`Strategy.UI` needs Chrome signed in to Clarity with the OpenCLI extension
loaded, and `opencli doctor` reporting the bridge connected.

- **The bridge is a machine-wide singleton.** One OpenCLI browser command at a
  time, and never alongside another CDP client (Claude-in-Chrome, Puppeteer, a
  DevTools session) against this site — they attach over the same protocol and
  evict each other with `Detached while handling command`.
- **If `opencli profile list` shows nothing connected**, `opencli daemon
  restart` usually recovers it within ~10–60 s, provided a Chrome window with
  the extension is open. Do **not** `pkill` an opencli browser process: it
  closes the window it owns, and if that was Chrome's last window the
  extension's service worker goes dormant and the bridge stays down.
- **If several OpenCLI extensions are installed**, check which one is actually
  enabled. Reading the version off a disabled copy tells you nothing about
  whether the bridge is up — that cost a wrong diagnosis during this build.
